DisputeDesk — Complete System Reference

What it is · How every piece works · Where every file lives · How to run it

1 · What DisputeDesk Is

DisputeDesk is a prototype AI-assisted tool that helps a bank's card-dispute analyst investigate credit and debit card disputes faster and more consistently.

When a customer claims a charge was wrong — fraud, item not received, duplicate charge, subscription cancelled — an analyst must decide within tight regulatory deadlines whether to file a chargeback, deny the claim, ask for more information, or escalate to a senior reviewer. DisputeDesk automates the evidence-gathering and rule-checking so the analyst can focus on the final judgement.

Key design principle: The AI never denies a customer on its own. It recommends; a human analyst always makes the final decision.

Built for the IBM SkillsBuild AI Experiential Learning Lab — track: Revolutionising Banking & Financial Services.

  • The analyst's browser — talks to /api/* endpoints and gets the HTML dashboard served from /.

4 · The Database (data/disputedesk.db)

SQLite. All synthetic data, generated once with random.seed(42), so every run is identical. The "world today" is 2026-10-15.

TableWhat it holds
customersIDs like CUST-0001, account open date
cardsCARD-0001, linked customer, Visa credit or debit, fake last-4
merchantsMERCH-001, fictional name, category (coffee_shop, online_retail…), is_online, refund policy
transactionsTXN-000001, amount, datetime, channel (in_store/online/recurring), device_id, shipping_address_id, statement_date
subscriptionsSUB-0001, monthly amount, start_date, cancelled_date (NULL if active)
shipmentsShipment_id, carrier, shipped/expected/delivered dates, delivery_status, proof_of_delivery
refundsRefund rows linked to transactions
disputesDSP-0001, complaint text in the customer's own words, status (open/resolved_customer/resolved_merchant/withdrawn)

The database is read-only for the FastAPI app. A second database — data/activity.db — is created automatically at runtime and stores tool call logs and analyst decisions.

6 · Backend Modules — What Each File Does

backend/app/main.py — Entry point

Creates the FastAPI app, registers CORS (all origins — tighten before production), attaches the activity-log middleware, mounts all routers, registers the /health endpoint, and finally mounts ui/ as a static-file SPA at /. The SPA mount must be last so API routes take priority.

backend/app/db.py — Read-only data DB dependency

Reads the env var DISPUTEDESK_DB (defaults to data/disputedesk.db relative to the repo root). Opens the SQLite file in read-only URI mode, sets row_factory = sqlite3.Row so columns can be accessed by name, and yields the connection as a FastAPI dependency. It closes the connection after the request finishes. If the file doesn't exist it yields None instead of crashing, so /health can still return {"database": "missing"}.

backend/app/activity_db.py — Writable activity DB

Opens (or creates) data/activity.db (overridden by env var ACTIVITY_DB). Creates two tables on first run: tool_calls (every /tools/* request with timing and HTTP status) and decisions (every analyst approve/edit/override action). Returns a plain sqlite3.Connection — callers close it themselves.

backend/app/middleware.py — Activity log middleware

A Starlette middleware that wraps every request. For any request whose path starts with /tools/ it records the tool name, dispute_id, transaction_id, HTTP status code, and duration in milliseconds into tool_calls. This happens automatically — the router code doesn't need to do anything.

backend/app/models.py — Shared Pydantic models

Currently holds HealthResponse (status: str, database: str). Router-specific models live in their own router files.

backend/app/routers/tools.py — 4 evidence-gathering tools

All mounted at /tools. These are the functions watsonx Orchestrate calls during an investigation:

EndpointOperation IDWhat it returns
GET /tools/disputes/{id}get_disputeFull dispute row + associated transaction, merchant, shipment, subscription, refunds, and customer history
GET /tools/transactions/{id}get_transactionTransaction row + card, merchant, shipment, subscription details
GET /tools/customers/{id}/historyget_customer_historyUp to 50 recent transactions, plus optional friendly-fraud signals when given a disputed_transaction_id and merchant_id
GET /tools/merchants/{id}get_merchant_infoMerchant details, plus shipment for a given transaction if transaction_id is passed

backend/app/routers/deadline.py — Deadline checker tool

Mounted at /tools. Endpoint: GET /tools/disputes/{id}/deadline?reason_code=…, operation_id check_deadline. Given a dispute ID and a Visa reason code it computes:

  • The 120-day card-network filing deadline from the transaction date (or expected delivery date for code 13.1)
  • Days remaining (negative = already past)
  • The Regulation Z notice window (60-day customer notice for credit cards)
  • The Regulation E notice window (60-day customer notice for debit cards)
  • Whether the dispute was filed in time

backend/app/routers/recommendation.py — Recommendation tool

Mounted at /tools. Endpoint: GET /tools/disputes/{id}/recommendation?reason_code=…, operation_id recommend_outcome. This is the brain of the agent-side logic. It:

  1. Loads all evidence for the dispute (transaction, shipment, refunds, signals, subscription, deadline)
  2. Applies the rule for the given Visa reason code
  3. Returns one of: file_chargeback / deny / request_more_info / escalate
  4. Returns a confidence (High/Medium/Low), the rule_applied in plain English, and a summary of the evidence used
  5. Saves the result to activity.db → recommendations so the dashboard can display it

backend/app/routers/api.py — Dashboard API (7 endpoints)

All mounted at /api. These are only for the analyst's browser — Orchestrate never sees them because the OpenAPI export script filters them out.

EndpointWhat it returns
GET /api/statsAggregate tiles: open disputes, by card type, by recommendation, by reason code, cases near deadline (≤14 days)
GET /api/casesPageable, filterable, sortable list of disputes with days_to_deadline and latest recommendation
GET /api/cases/{id}Full case detail: dispute + transaction + shipment + subscription + refunds + friendly-fraud signals + deadline + latest recommendation + decision history
POST /api/cases/{id}/decisionRecord an analyst decision (approve / edit / override) with final outcome, reason, and analyst name
GET /api/activityTool-call rows since a given ID (used for live polling by the dashboard)
GET /api/auditTool calls + analyst decisions merged and sorted by timestamp — the full audit trail
GET /api/evaluationCompares saved recommendations against data/cases.csv answer key, returns accuracy score

7 · The Analyst Dashboard (ui/)

A single HTML file with no build step. Loaded from ui/index.html, served by FastAPI's StaticFiles at /. Uses Chart.js (CDN) for charts. All styling is plain CSS.

TabWhat it shows
Overview4 stat tiles (open, investigated, escalated, deadlines at risk), bar chart by reason code, donut chart of recommendations, agent accuracy card vs. the answer key
Case QueueFull case table with filter dropdowns (status, card type, recommendation, deadline window), free-text search, sortable columns, colour-coded badges. Click a row to open the case.
Case DetailCustomer's complaint quote, transaction and shipment facts, friendly-fraud signal dots, 4-point deadline timeline (transaction → statement → filed → network deadline), agent recommendation with 4 evidence checks ✅/❌, Approve / Edit / Override buttons (edit and override require a reason and analyst name), full decision history, "Investigate with DisputeDesk" button that copies the prompt and opens Orchestrate
Agent Activity5-stage pipeline (Intake → Evidence → Compliance → Decision → Letter) with the active stage highlighted. Polls /api/activity every 2 seconds. Shows a live list of tool calls with time, stage, tool name, dispute ID, HTTP status, and duration. Shows "Waiting for agents…" when idle.
Audit LogMerged timeline from /api/audit showing every tool call and analyst decision in chronological order. Filterable by dispute ID.

ui/config.js holds one setting: ORCHESTRATE_CHAT_URL. Set it to your watsonx Orchestrate chat permalink so the "Investigate" button opens the agent directly.

10 · How to Run — Step by Step (macOS)

First time setup

# 1. Clone or open the repo
cd "/Users/vishnu/Desktop/IBM SkillaBuild/Dispute Desk"

# 2. Create a virtual environment
python3 -m venv .venv
source .venv/bin/activate

# 3. Install dependencies
pip install -r requirements.txt

# 4. (Optional) Regenerate synthetic data — only needed if you delete the DB
python3 data/generate_data.py

Start the API + dashboard

source .venv/bin/activate   # if not already activated

python3 -m uvicorn backend.app.main:app --reload --port 8000

Then open http://localhost:8000 in your browser for the analyst dashboard.
The interactive API docs are at http://localhost:8000/docs.

Run all tests

python3 -m pytest          # runs all 110 tests
python3 -m pytest -v       # verbose — shows each test name
python3 -m pytest backend/tests/test_tools.py  # one file only

Re-export the OpenAPI spec for Orchestrate

python3 agent/export_openapi.py
# writes agent/disputedesk_tools_openapi.json

Environment variables (optional overrides)

VariableDefaultPurpose
DISPUTEDESK_DBdata/disputedesk.db (repo root)Path to the main SQLite database
ACTIVITY_DBdata/activity.db (repo root)Path to the writable activity log database
